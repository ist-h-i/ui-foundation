# 実装・検証計画

このリポジトリの現在の完了範囲は、要件・設計・開発構成の保存とGitHubへの初回pushです。以下は今後の計画で、実装済みの機能を示しません。

## 段階1：設定と生成

1. `src/config.ts` と設定試験：contextと機械設定を分離した最小スキーマを確定し、未対応版、必須値、enum、パス範囲、例外の形式を検証する。自然言語の変更だけで視覚設定を推測しないことを確かめる。
2. `presets/task-oriented/` と解決試験：共通の型付き設定を得る。同じ入力とツール版で同じ結果を得て、対象外の機能仕様を取り込まない。
3. `src/cli.ts`、`src/sync.ts` と生成試験：init／sync、dry-run、冪等性、衝突と手編集検出を実装する。既存AGENTS／packageの管理外部分、custom、機能を保全し、dry-runが書き込まないことを確認する。
4. `templates/angular/`、`skills/ui-development/`：五つの部品群、スタイル、Skill、検査設定を同じ解決設定から生成する。処理中の操作抑止など一つの方針が三出力へ一致して反映されることを確認する。

最小の次作業は1です。対応版と例外構造を記録し、有効な設定例が受理され、不正な設定を位置・理由付きで拒否する試験を先に定義します。CLI全体や画面一式を一度に実装しません。

## 段階2：逸脱検知

`src/checks/` に設定・生成物の一致検査と、TypeScript AST／Angularテンプレート／CSS解析に基づく限定ルールを置きます。

検証fixtureには、規則に適合する例、実際の逸脱、正当なトークン値・計算値、対象外コード、理由付き例外、動的で判定不能な例を含めます。利用箇所の件数は分類と分母を示し、import数やUX総合点を出力しません。未同期・手編集・未知を成功扱いせず、診断と重大度を確認します。

## 段階3：実利用検証

`tests/fixture-app/` に一覧と編集フォームを持つ小さなAngularアプリを作ります。フォーム送信、不可逆操作、部分障害、結果不明、実データを戻すUndoを含め、Playwrightで応答・失敗を制御して次を確認します。

| シナリオ | 観測する結果 |
| --- | --- |
| 処理中に再操作 | 二重実行されず、処理中と認識できる。 |
| 入力エラーの修正 | 値が残り、該当箇所を直して継続できる。 |
| 一つの取得だけ失敗 | 正常な独立領域が使え、欠損と影響が残る。 |
| 更新結果が不明 | 成功・失敗を偽らず、安全な確認へ進める。 |
| Undo | 対象の実状態が復元される。 |
| キーボード、タッチ、画面幅 | 重要操作、focus、状態表示が失われない。必要なクリック／タップ代替がある。 |
| 動きを減らす設定 | 因果関係や状態の意味を維持できる。 |
| Skillの選択 | UI依頼で選ばれ、非UI依頼で不要に適用されない。 |

共通部品の試験と利用アプリの業務試験を分けます。自動アクセシビリティ検査、手動確認、多様な利用者の確認を組み合わせます。描画例外の隔離はMVPの合格対象へ混ぜません。

## 比較する価値

同じ小さな課題で「Skillだけ」と「Skill＋共通部品＋検査」を分け、再説明、逸脱、手戻り、失敗時の復旧を比較します。ケース、環境、観測方法、判定不能を保存し、少数ケースをあらゆるUIでの効果とみなしません。共通化の入力や例外処理が効果を上回る場合は共通化を縮小します。

## コマンドと完了報告

現在の `package.json` に検証・生成コマンドはありません。実装と有効な試験が揃った段階でローカルnpmコマンドを追加します。利用アプリ側では `ui:sync`、静的な `ui:check`、Playwrightによる `ui:test` を分けます。未実装の処理を成功するダミーにしません。GitHub Actionsやnpm公開をMVPの完了条件には含めません。

各段階の報告は変更範囲、実行したコマンド、観測した結果、残る未実装・未検証を示します。失敗した変更はGitの差分から修正・復元できる状態を保ち、利用者の管理外ファイルを上書きしません。
