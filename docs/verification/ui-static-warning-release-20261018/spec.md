# 警告の全件分類と取り込み

## 目的と完成の範囲

指定ソースの静的検査を、理由不明の警告を放置しない状態で取り込む。既知の違反は修正し、残す警告には具体的な生成経路・契約・検証範囲・残る境界・再確認条件を付ける。静的検査の完成と、任意の実行時入力・外部描画・視覚・アクセシビリティ全体の保証は分ける。

ユーザーは本タスクのcommit・push・通常mergeを認可している。npm公開は対象外。

## 受入条件

1. 最新の通常CLIで得た警告を一対一に分類する。警告数を減らすための包括的例外やUnknownの成功扱いを行わない。確定違反は既存の終了1を維持する。
2. 全警告を3担当で調査し、主担当が根拠を確認する。改善候補があれば再現・回帰を先に用意し、必要な検査器/実装修正を行う。
3. リポジトリ用の分類台帳に、診断の正確なidentity、理由、producer、既存の有限検証、未保証範囲、再確認条件、根拠ファイル/anchor/hashを記録する。
4. 分類検査は新規/未分類の警告、重複、消滅した分類、欠損/不正な台帳、根拠hash/anchorの変化を失敗にする。エラーを警告台帳で承認できない。元の診断を削除・変更しない。
5. この分類検査は本リポジトリの受入チェックであり、利用アプリのYAML schemaや同梱CLIの「警告のみなら終了0」の契約を変更しない。通常のnpm testから実行する。
6. 正負の回帰、通常test、検証ツール、型、build、生成同期、同梱版、影響するcross-browser回帰を確認する。各実行のsource前後・command・終了状態・logを保存する。省略や失敗は明記する。
7. 新規の分類機能と、今回取り込む未コミットの静的検査/関連runtime修正を、正確なbase/headのfresh reviewerへ領域別に渡す。修正必須指摘を確認・解消する。
8. 必要なソース、生成物、試験資材、分類と最終検証記録をcommitする。以前からの大きなローカルtrace・一時checkout・比較snapshotを無差別にGitへ追加しない。過去記録のbytesは保持する。新しいclean checkoutだけでテストに必要な資料が揃うことを確認する。
9. push・PRの通常mergeを行い、リモートmainのmerge SHAとレビュー済みheadの包含を確認する。空のCI登録をCI成功としない。

## 実装の最小範囲

- `src/warning-review.ts`: 台帳検証と診断対応の純粋なロジック、root内の根拠ファイルの読取り。
- `src/warning-review-cli.ts`: 本リポジトリのcheckProjectと台帳を使う入口。text/JSONと終了状態を返す。
- `docs/ui-warning-reviews.json`: 全警告の理由と根拠。汎用的なallowlistにはしない。
- `tests/static/warning-review.test.ts`: 新規・古い・重複・不正・error・hash/anchor・pathの回帰。
- packageの検証入口と、現在の分類/受入手順の文書。

## 検証と差戻し

raw CLIと分類検査を分け、同じSourceReportを変更しないことを検証する。分類台帳の変更はソースの修正と根拠の再確認に基づけ、自動で全件承認する更新コマンドは作らない。取込み前に不備があればPR上で修正し、通常mergeを拒否する条件を迂回しない。
