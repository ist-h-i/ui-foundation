以下のプロジェクトを始めます。
ローカルマックに新しいフォルダを作成して、GitHubにプッシュして新しいリポジトリを作成してください。

結論

「プロジェクトのUI方針から、共通部品・AI向けSkill・検査設定をまとめて生成する小さな開発ツール」にするのが適切です。

中心に置くのは、AIによる自由生成ではなく、次の構造です。

> 人が方針を決める → AIが設計を支援する → 承認した設定をコードと検査に固定する → 以後のAI開発も同じ基盤を使う。



最小構成は、設定ファイル1つ、CLI1つ、Skill1つ、小さなUI部品群、ローカル検査です。AI API、サーバー、データベース、ASKのRouterやLedgerは不要です。

ただし、最初に重要な区別があります。共通化するのは「すべての画面の見た目」ではなく、設計の判断基準、部品の使い方、状態と操作の意味です。 一覧画面と編集画面を同じレイアウトにする必要はありません。

1. このセッションで合意してきたこと

会話全体を、今回の新プロジェクトへ持ち込む要件として整理すると次のようになります。

領域	最終的に目指すこと

人間中心設計	利用者、利用状況、達成したいことから設計する。システム内部の処理順やデータ構造を、そのまま画面にしない。
情報設計・視覚階層	主情報、判断材料、補助情報を区別し、何を見るべきか分かるようにする。巨大な抽象タイトルや同じ強さのカードを並べるだけにしない。
言葉遣い・説明	UI文言を対象とする。短く自然なラベルや操作結果を予測できる文言を使い、同義のタイトル・サブタイトル・説明を重ねない。文章一般の品質管理へは広げない。
アフォーダンス・シグニファイア	操作できる対象と操作方法を知覚できるようにする。見た目だけでなく、意味を持つコントロールと状態表現を使う。
振る舞いの一貫性	押下、選択、focus、loading、error、画面遷移、出現・消失などに共通の意味を持たせる。ここでの「Material Design」は、特定製品ではなくこの考え方を指す。
直接操作・フィードバック	対象と結果の対応が分かる操作を使う。動きは因果関係や連続性を伝えるために使い、装飾として強制しない。
ユニバーサルデザイン	能力、経験、端末、入力方法の違いで不必要に排除しない。色、アイコン、hover、ドラッグなど、一つの手掛かりや操作方法だけに依存しない。
可逆性・結果の予告	可能な操作はUndo、取消、復元、再編集を可能にする。不可逆操作は、対象・影響・戻せないことを実行前に伝える。
部分障害への耐性	安全に使える正常部分と入力内容を維持する。部分障害は隠さず、欠損を正常値や完全な結果に見せない。
完了・継続	現在地、処理結果、完了、戻り、次の行動までつなげる。
AI開発への適用	大量の常時ルールではなく、必要時に読むSkillと事例を使う。機械で判定できる部分はスクリプトへ移す。
検証・改善	静止画だけでなく実際の操作・失敗・復旧を検証する。要素数や部品使用率を、そのままUXの良さとは扱わない。


Design Harnessの議論から引き継ぐのも、特定サイトの見た目ではなく、制約・プロジェクト文脈・検証・評価をつなぐ構造です。

以前の表現で、補正しておくべきこと

「追加より削除」「1画面1目的」「主操作は1つ」は、無条件の禁止ルールにしません。

判断に必要な比較情報まで削る、ダッシュボードを無理に単一操作へ分解する、明確な「設定」というタイトルを長い動作文に変える、といった修正は改善ではありません。

原則は、不要な負担を減らし、必要な理解と操作性を保つことです。今回のツールも「簡素な画面しか作れない仕組み」にはしない方がよいです。

2. AIと非AIの責任を分ける

「AIがコードを書くか」と「実行時にAIが制御するか」は別です。AIが実装した部品でも、完成後は通常のプログラムとして決定的に動かせます。

推奨する責任分担は次です。

対象	AIが担当すること	非AI側で固定・実行すること	人が決めること

プロジェクト理解	資料や要件から設定案を作る	YAMLの構造・必須値を検証する	対象者、目的、重要な制約
UI方針	適した情報密度、構成、表現を提案する	採用済みプリセットと設定を解決する	提案の採否
基礎部品	新しい部品が必要か判断を支援する	検証済みテンプレートから生成する	共通部品として採用する範囲
個別画面	必要情報を選び、部品を組み合わせて実装する	型、API、状態処理、共通スタイルを実行する	業務上の正しさ、重要な例外
UI文言	ラベル、説明、エラー文を文脈に合わせて作る	用語統一や検出可能な表記違反を検査する	意味や対外表現の重要判断
状態・操作	必要な状態や復旧経路を設計する	状態遷移、二重操作防止、focus管理などを実行する	業務上許される操作
可逆性・部分障害	影響範囲や必要な復旧を整理する	アプリ側が実データの復元・整合性を保証する	不可逆性、継続利用の安全範囲
品質確認	目的適合性、情報優先度、分かりやすさをレビューする	静的検査と操作テストを実行する	実利用での有効性、受け入れ


MVPでは、CLIからLLMを呼ばない構成を推奨します。

既存のコーディングAIにSkillを読ませれば、設定作成や画面実装を支援できます。パッケージ自身がモデル選択、APIキー、課金、再試行を管理する必要はありません。

その結果、生成と検査はAIなしでも動き、設計判断が必要なところだけAIを使う構成になります。


---

3. 全体構成は「設定から三つを同時生成する」

最も重要なのは、部品・AI向け指示・検査設定を別々に作らないことです。

プロジェクトの要件・既存実装
          ↓
   人／AIが設定案を作成
          ↓
   ui.config.yaml を確定
          ↓
   CLIが検証・設定解決
          ↓
     共通の設定オブジェクト
          ├─ UI部品・スタイルを生成
          ├─ プロジェクト用Skillを生成
          └─ 静的検査の設定を生成

以後の開発
  変更依頼
    → AIがSkillと必要なプロジェクト文脈を読む
    → 共通部品を使って個別画面を実装
    → 静的検査・操作テスト
    → 必要な意味・視覚レビュー

例えば「処理中のボタンは再実行させず、処理中であることを伝える」という方針なら、同じ定義から次の三つを作ります。

出力先	反映内容

UI部品	処理中の表示、操作抑止、支援技術へ伝える状態
Skill	非同期操作でその部品を選び、実際の処理状態を接続する指示
検査・テスト	必要な状態接続と、処理中の再操作を確認する観点


ルール文には書いてあるのに部品では実現できない、部品は対応しているのに検査が知らない、という分裂を防ぐ設計です。

ただし、共通設定から生成できるのは共通部分までです。各業務操作の成功条件や復元処理までは、自動的に決まりません。


---

4. YAMLには「プロジェクトの判断材料」と「確定設定」を分けて持たせる

YAMLを、全画面の仕様を書く巨大な言語にはしません。まずは、繰り返し使うプロジェクト情報と共通方針に限定します。

以下は提案する設定例です。実装済みのスキーマではありません。

schema_version: 1

context:
  product: 申請管理
  users:
    - 申請者
    - 承認担当者
  goals:
    - 必要な情報を確認して、提出・承認・差し戻しを判断する
  usage: 業務中に繰り返し利用する
  constraints:
    - 未取得の情報を、確認済みの情報として表示しない
    - 入力内容を部分障害で失わせない

target:
  framework: angular
  source: src/app
  generated_ui: src/app/shared/ui/generated

design:
  preset: task-oriented
  density: standard
  locale: ja

components:
  - page-frame
  - action-control
  - form-field
  - async-region
  - action-feedback

checks:
  include:
    - src/app/features/**
  raw_design_values: error
  unapproved_controls: error
  copy_candidates: warning

exceptions: []

自然言語と機械設定を混同しない

context はAIが判断に使う情報です。target、design、checks は、CLIが解釈する型付きの設定です。

例えば、

> 「初心者にも使いやすくしたい」



という文章から、スクリプトが勝手に「説明文を増やす」「文字を大きくする」「項目を隠す」と決めてはいけません。AIが候補を提案し、必要なものだけ確定設定にします。

一般原則は毎回入力させない

「色だけに依存しない」「状態を明示する」「部分障害を隠さない」といった共通原則は、パッケージのプリセットに持たせます。

ユーザーに毎回入力させるのは、主に誰が何のために使うか、既存の制約は何か、標準と違う判断は何かです。

個別機能の状態遷移や業務ルールは、その機能のコード・テスト・仕様に置きます。全機能をYAMLへ集約すると、アプリケーション仕様と二重管理になります。

5. npm導入は、インストールと初期化を分ける

「npmで導入して、設定と部品を生成する」という体験はそのまま採用できます。

ただし、postinstallで利用者のソースや設定を自動変更する方式は避けます。 npmのライフサイクルスクリプトは再インストールやnpm ciでも実行対象になり、ignore-scriptsによって無効化される場合もあります。初期化をインストール時の副作用にすると、実行時期が分かりにくくなります。

推奨する操作は次です。パッケージ名とコマンド名は仮称です。

# 開発ツールを導入
npm install --save-dev --save-exact @your-org/ui-foundation

# 設定の雛形と開発コマンドを用意
npx ui-foundation init

# ui.config.yamlを編集・確認した後に生成
npm run ui:sync

# 以後の開発で検査
npm run ui:check
npm run ui:test

CLIの主コマンドは、最初は三つで足ります。

コマンド	役割

init	設定雛形、Skillへの導線、package.jsonのスクリプトを追加する。既存設定は破壊しない。
sync	設定から共通部品、スタイル、Skill、検査設定を生成・同期する。
check	設定不正、生成物の不整合、実装の規約違反、標準経路の利用状況を検査する。


package.jsonは次のようにします。

{
  "scripts": {
    "ui:sync": "ui-foundation sync",
    "ui:check": "ui-foundation check",
    "ui:test": "playwright test tests/ui"
  }
}

ui:checkは静的検査、ui:testは実ブラウザーでの操作検証です。静的検査が成功しただけで「振る舞いも確認済み」と扱わないように分けます。

6. 生成するのは「画面一式」より「判断を実装済みにした部品」

最初からカード、モーダル、タブなどを大量に生成する必要はありません。それでは、会話の出発点だった「使える部品を何でも並べるUI」に戻ります。

MVPでは、次の五つの部品群を推奨します。

部品群	固定する内容

PageFrame	タイトル、判断材料、本文、主要操作の配置基準。不要なサブタイトルを自動挿入しない。
ActionControl	通常、focus、押下、処理中、無効、重大操作の表現。ボタンとリンクの意味を分ける。
FormField	ラベル、必須・任意、入力補助、エラーの関連付け。選択系では選択状態も明確にする。
AsyncRegion	領域単位の取得中、正常、空、更新失敗、部分欠損と、局所再試行の表示。
ActionFeedback	実行結果、復旧操作、実際に利用可能なUndo、不可逆操作の影響説明。


これらに、共通の文字・余白・色・状態・モーションの設定を組み合わせます。

独自コントロールを一から作ることは目的にしません。 初版はHTML標準要素や既存の基礎部品を活用し、必要な振る舞いだけを補います。Angular公式も、可能な場合には標準HTML要素を再利用する方針を示しています。

カードは必要な独立情報をまとめる選択肢として残せますが、「すべての情報をカードにする」既定値にはしません。

共通化するのは見た目だけでなく状態の意味

例えば、次は異なる状態です。

- キーボードでfocusがある。
- 選択されている。
- 操作できない。
- 操作を受け付けて処理中である。

これらを同じ薄い色や一つのactiveフラグで表現しない設計にします。状態の意味を共通化してから、その状態に対応する見た目を決める順序です。

動きについても「必ずアニメーションする」ではなく、必要な連続性を伝え、動きを減らす設定では意味を失わない表現にします。ドラッグ操作には、必要に応じてクリック・タップで実行できる代替を用意します。キーボード代替があるだけでは、ドラッグできないタッチ利用者への代替にならない点にも注意が必要です。

7. 可逆性と部分障害は、アプリ側との責任境界を明確にする

この二つは、本プロジェクトの価値になります。ただし、部品を配置するだけで保証できるものではありません。

可逆性：Undo表示と実データの復元は別

UI基盤の責任	アプリケーションの責任

Undoの表示方法を統一する	復元可能かを判断し、実際に復元する
不可逆操作の説明を表示する	対象・影響範囲・不可逆性を正しく渡す
処理中、成功、失敗、結果不明を区別する	APIの結果や処理状態を正しく渡す
取消可能なときだけ取消を出す	取消の対象が待機処理か、実行中処理かを定義する


通信を中断したことを「変更を取り消した」と表示してはいけません。 また、応答が届かなかっただけで失敗と決めつけ、再実行によって二重更新を起こす設計も避けます。

共通部品は安全な経路を使いやすくしますが、復元処理や更新の重複防止はアプリ側に残します。重要な操作について可逆・確認・検証の経路を設ける考え方は、WCAGのエラー防止の説明とも対応します。

部分障害：描画できる範囲と、信頼できる範囲は別

例えば、申請一覧と参考統計を表示する画面で、参考統計だけ取得に失敗した場合は一覧を維持します。

一方、承認判断に必要な情報が欠けているなら、一覧を描画できても承認操作は止める必要があります。

推奨する原則は次です。

> 正常部分は維持する。欠損の影響を伝える。誤った判断につながる結果と操作だけを止める。



AsyncRegionに持たせるのは、この状態を表示する仕組みです。データの依存関係や安全な継続範囲を、部品が推測してはいけません。

また、データ取得エラーの局所表示と、コンポーネントの描画例外を隔離することは別です。描画例外まで隔離できると主張するには、対象フレームワークで実装・検証された境界が必要です。MVPでは、対応する障害の種類と未対応の種類を明示します。

未解決の障害は一瞬のトーストだけで済ませず、影響する領域に残します。状態メッセージは見えるだけでなく、必要に応じて支援技術にも伝えられるようにします。

8. AI向けには「大量のルール」ではなく、生成されたSkillを渡す

当初の「ルールを適切なところへコピーする」は、コピーと同期をCLIが管理する形に変えるのがよいです。

手作業でコピーすると、元の設定を変えた後も古い指示が残りやすくなります。

Skillは、主に次の判断手順を持ちます。

1. 今回の変更に関係する利用者・目的・制約を読む。
2. 既存画面と共通部品を確認する。
3. 必要な情報、操作、状態、失敗時の動きを整理する。
4. 共通部品と既存パターンで実装する。
5. 規約外の実装が必要なら、理由と影響を明らかにする。
6. 静的検査と対象シナリオを実行する。
7. 実画面の目的適合性をレビューする。

詳細な反例やパターンは、必要になったときに読む参照ファイルへ分けます。この構成は、Agent Skillsの段階的な読み込みと整合します。

Codexを初期対象にする場合、プロジェクト内の.agents/skills/へSkillを配置できます。AGENTS.mdにはUI変更時のSkill参照と検査コマンドだけを短く残す構成が考えられます。

ただし、Skillを置くことと、確実に適用されることは別です。導入検証には、UI依頼でSkillが選ばれること、非UI依頼では過剰に適用されないことも含めます。

常時指示は入口、Skillは判断支援、部品と検査は実装上の制約、という分担です。


---

9. 検査は三層に分ける

「UI/UXルール違反を全部スクリプトで判定する」は目指しません。

A. 静的に判定できるもの

検査対象	例

設定・生成物の整合性	YAML変更後にSkillや部品が未同期、生成物の手編集
デザイン値の逸脱	対象領域での未承認の色、余白、文字サイズ、アニメーション時間
部品利用の逸脱	共通操作部品を使わず、機能側に別のボタン挙動を実装
プロパティの不正	許可されていないvariant、必須の状態や名前の欠落
検出可能な言語問題	用語の不一致、既知の冗長表現、表記ゆれ
構造上の危険	許可されていない直接DOM操作や、基盤の状態表現を壊す上書き


判定は正規表現だけで済ませず、TypeScript・テンプレート・CSSをそれぞれ解析します。Angularのテンプレート向け独自ルールはangular-eslint、CSS側はStylelintの拡張機構を利用できます。毎回AIに検査コードを生成させるのではなく、検証済みルールへ設定値を渡す方式です。

ただし、禁止するのは「あらゆるハードコード」ではありません。トークン定義内の値、計算に必要な値、適用範囲外のコードまで一律に禁止しないことが重要です。解析できない動的な指定は、確認済みの適合とは扱いません。

日本語検査も同様です。textlint-ja系の知見を使いつつ、短いラベルに本文用の句点や文体ルールを強制しないよう、UI文言の役割に合わせます。技術文書向けプリセットも、文章に応じた設定調整を前提としています。

B. 実操作で確認するもの

共通部品の試験に加えて、利用アプリで次を確認します。

シナリオ	確認する結果

非同期処理中に再操作する	二重実行されず、処理中と分かる
入力エラーを修正する	入力内容が残り、該当箇所を直して継続できる
一つの取得処理だけ失敗する	独立した正常部分は使え、失敗と影響範囲が分かる
更新結果が不明になる	成功・失敗を偽って表示せず、安全な確認経路へ進める
Undoを実行する	表示だけでなく対象の状態が復元される
キーボードや異なる画面幅で操作する	重要操作、focus、状態表示が失われない


Playwrightでは通信をモックし、特定の応答や失敗状態を作る試験が可能です。これを使って、正常系だけでは見えない挙動を検証します。

C. AI・人が判断するもの

画面の目的が伝わるか、情報の優先順位が適切か、説明を削りすぎていないか、比較や判断がしやすいかは、別途評価します。

自動アクセシビリティ検査でも、すべての問題を検出できるわけではありません。自動検査・手動評価・多様な利用者による確認を組み合わせる必要があります。

ui:checkの成功は「機械検査対象に違反が見つからなかった」という意味に限定し、UX全体の合格にはしません。

部品使用率は「逸脱の所在」を示す

使用率は実装できますが、分母を明示します。

例えば、次のような出力です。

操作コントロールの静的な利用箇所

標準部品・承認済み経路     24
標準外                    2
明示された例外            1
判定できない動的実装      3

これは説明用の例で、実測値ではありません。

import件数ではなく、実際の利用箇所を数えます。ただし、テンプレートのループは静的には一箇所であり、画面に表示された実数や利用頻度とは異なります。

未分類と例外を隠して「使用率100%」にしないこと、使用率を上げるために不要な部品を追加させないことが重要です。

10. ファイル構成と再生成の方針

開発するパッケージ

最初は単一リポジトリ・単一npmパッケージで十分です。

ui-foundation/
├── package.json
├── src/
│   ├── cli.ts
│   ├── config.ts
│   ├── sync.ts
│   └── checks/
├── presets/
│   └── task-oriented/
├── templates/
│   └── angular/
├── skills/
│   └── ui-development/
└── tests/
    ├── config/
    ├── generation/
    ├── checks/
    └── fixture-app/

CLI、Skill、部品テンプレート、検査ルールを、最初から別パッケージに分けません。フレームワーク対応も、初版は普段の開発領域に合わせてAngular／TypeScriptへ限定する案を推奨します。

利用プロジェクト

利用プロジェクト/
├── ui.config.yaml                 # 人が管理する設定の正本
├── .ui/
│   └── generated/
│       ├── policy.json
│       ├── tokens.css
│       └── manifest.json
├── .agents/skills/project-ui/     # 設定に合わせて生成
├── src/app/shared/ui/
│   ├── generated/                # CLI管理の共通部品
│   └── custom/                   # 個別拡張
├── src/app/features/             # 人・AIが開発する機能
├── tests/ui/                     # アプリ固有の操作試験
├── AGENTS.md
└── package.json

policy.jsonは生成物であり、二つ目の正本にはしません。検査は、YAMLから解決した設定との一致も確認します。

再生成で開発成果を壊さない

生成ツール自身にも、今回議論した可逆性と結果の予告を適用します。

- sync --dry-runで変更対象と差分を確認できる。
- 同じ設定・同じツール版なら、再実行しても不要な差分を出さない。
- 前回生成したファイルの内容を記録し、手編集を検出したら黙って上書きしない。
- 既存のAGENTS.mdやpackage.jsonは、管理対象部分だけを変更する。
- 個別拡張や機能コードは再生成しない。

設定、生成元バージョン、生成物をGitで追えるようにします。生成結果をAIが直接直し、その次の生成で消える運用を避けることが継続利用の前提です。

11. MVPは「一つの画面を継続改善できる」範囲で成立させる

初版の目的は、全UIパターンを網羅することではありません。

> 一度設定した方針を説明し直さずに次の画面を開発でき、共通挙動の逸脱を検知し、必要な例外は理由付きで扱える。



この状態を最小の実装で確認します。

段階	実装するもの	確認する価値

1. 設定と生成	YAML、プリセット、init／sync、Skill、少数の部品	同じ入力から一貫した基盤を再生成できる
2. 逸脱検知	静的検査、生成物の同期確認、標準経路の利用状況	AIが共通基盤を迂回した箇所を特定できる
3. 実利用検証	フォーム送信、不可逆操作、部分障害を含む小さなアプリ	正常時だけでなく失敗時にも意図した体験が成立する


最初の検証アプリは、一覧と編集フォームがあり、一部情報だけ取得失敗させられるものが適しています。情報階層、入力、選択、非同期処理、エラー、可逆性を一つの小さな題材で確認できます。

比較では、少なくとも「Skillだけ」と「Skill＋共通部品＋検査」を分けます。後者が本当に再説明や手戻りを減らすかを確かめます。少数ケースの結果を、あらゆるUIでの効果として一般化しないことも必要です。

初版で作らないもの

ASK連携、複数フレームワーク対応、AI API内蔵、独自の大規模デザインシステム、全画面を記述するYAML DSL、自動学習Ledger、UXの総合点、管理ダッシュボードは対象外にします。GitHub Actionsも完了条件には含めず、ローカルのnpmコマンドで成立させます。

また、既存部品とSkillだけで十分なところは、新しい部品を作りません。共通化のための例外処理や入力負担が、減らせる手戻りを上回るなら、その共通化は縮小すべきです。

最終的な戦略

今回作るものは、「AIに良いUIを作らせる長い指示集」でも、「YAMLから全画面を自動生成するプラットフォーム」でもありません。

プロジェクトのUI方針を、AIが読める判断基準と、通常のコードとして動く共通部品と、逸脱を検出する検査へ、一貫して変換する開発基盤です。

AIには、利用者の目的に合わせた情報選択、画面構成、文言、例外判断を担当させます。一方で、採用済みの見た目・状態・操作の規則、生成、同期、検査、実行時の動作は、通常のソフトウェアに固定します。

最初に固めるべき設計は、YAMLの最小項目、生成物の所有範囲、共通部品とアプリの責任境界、機械検査で断定できる範囲の四つです。ここを先に決めれば、シンプルな構成のまま、今回の議論を実際の開発へつなげられます。
