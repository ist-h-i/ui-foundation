# 0007　生成アイコンの描画とデータを分ける

2026年11月25日採用。対象は Angular の生成元と公開入口。製品への実装・配布は後続とする。[Issue #56](https://github.com/ist-h-i/ui-foundation/issues/56)・[測定条件と横展開の結果](../verification/generated-icon-loading-56/README.md)

## 判断の根拠

検索アイコン1個を表示するだけで、Angular 21・22 の開発サーバーは遅延ルートに約50 MB の JavaScript を配信した。登録を12個から1個に減らしても、検索専用の Angular コンポーネントに替えても再現した。いずれも `@lucide/angular` の全アイコンを収めた単一の ES モジュールを読み込む。開発時の応答には未使用アイコンの実コードが残り、インラインのソースマップがさらにサイズを増やす。`ActionControl` はアイコン指定が空でも描画部品を静的に参照するため、ボタン・リンク・カードにも波及する。[現行の Icon](../../templates/angular/icon.ts)・[ボタンとリンク](../../templates/angular/action-control.ts)・[カード](../../templates/angular/card.ts)

Angular 22 で公開版から生成した `core` の検索アイコンは、遷移時に 51,580,684 B を取得した。生成元を差し替えた試作では、既存の `core` 経由で 850,579 B、アイコン専用入口から検索1件を登録すると 21,808 B、既定12件でも 33,317 B になった。専用入口の検索1件は最適化ビルドでも空のアプリからの増加が 12,360 B だった。`core` に残る共有辞書が専用入口の要否を分けた。[比較表](../verification/generated-icon-loading-56/README.md#公開入口を変える効果)

## 採用する方式

- 開発元で `@lucide/icons@1.52.0` の公開個別入口から図形を取り、型付きのデータをアイコンごとに生成してパッケージに同梱する。既定12種類は名前・別名・形状・寸法まで現行の Angular 版と一致した。利用アプリは `sync` で受け取り、通常の表示に Lucide の実行パッケージを必要としない。既定12件の明示リストを生成と照合の正本にする。動的な名前の利用を維持するため、利用側のテンプレート走査で採否を決めない。[上流のデータ形式](https://lucide.dev/guide/icons)・[1.52.0 の公開入口](https://github.com/lucide-icons/lucide/blob/1.52.0/packages/icons/package.json#L27-L48)
- 描画部品は名前を DI のレジストリで解決し、許可した図形・属性から SVG を組み立てる。`angular/icons` で描画と選択登録、`angular/icons/defaults` で既定12件の登録、`angular/icons/search` など生成した図形ごとの公開ファイルで個別データを提供する。遅延ルートで追加した図形が初期画面に入らない構造にする。`core` と `index` は同じ実装の `Icon` と `provideUiIcons` を引き続き公開する。静的検査はこれらの公開ファイルを個別に認め、内部の描画やレジストリへの直接参照は引き続き検出する。[既存の入口に関する決定](0006-angular-state-and-io.md)・[静的検査の公開入口一覧](../../src/check/application.ts)
- `<ui-icon name="…">`、動的な名前、`size`、`severity`、`decorative`、`label` と、`provideUiIcons()` の既定12件を保つ。追加登録は従来のクラスの公開 `.icon` と構造化データを受け入れる。`LucideFolder` 等を利用側が Angular 版から import する経路には、そのパッケージの取得コストが残る。選択登録時も、メニューなどが必ず使う図形は当該部品から個別に参照し、利用側の名前・別名による上書きを優先する。
- Lucide の DI を直接併用するアプリ向けに、明示的に選択したときだけ互換入口を生成する。既存の `provideUiIcons` から生の `svg[lucideIcon]` を描く方向と、外部の `provideLucideIcons`・`provideLucideConfig` から `ui-icon` を描く方向の両方を扱う。通常の `core`、全件の `index`、生成された型の解決経路から、この任意依存を切り離す。DI を共有している既存アプリには更新前に互換入口への切り替えを案内し、両方向の試験と移行手順を同じリリースに含める。[Lucide の DI 実装](https://github.com/lucide-icons/lucide/blob/1.52.0/packages/angular/src/lucide-icons.ts)
- `sync` の既存の所有権・ハッシュ・古い生成物の削除規則を使う。配布時に Lucide の ISC と Feather 由来の MIT の著作権・ライセンス表示を保つ。既定データと生成元を固定し、ネットワークなしでも同じ設定から同じ出力を得られるようにする。[生成処理](../../src/sync.ts)・[上流ライセンス](https://github.com/lucide-icons/lucide/blob/1.52.0/LICENSE)

## 実装の受入条件

1. npm 配布候補から生成した最小アプリを、報告側の Angular 21.1.4 と基盤側の 22.3.0 で検証する。開発時は最適化なし、ソースマップあり、CLI キャッシュ無効。初期表示と初回遷移で取得した JS の合計と最大応答を別々に記録する。空ルートからの増加は、検索1件の専用入口で遷移時最大・初期から遷移完了までの合計を各 100,000 B 以下、既定12件の同合計を 200,000 B 以下とする。本番最適化では検索1件の初期＋遅延 JS の増加を 20,000 B 以下とする。いずれも同一条件の非圧縮バイトで比較する。
2. Lucide の実行パッケージをインストールしていないアプリで軽量入口と基本部品を AOT ビルドし、検索アイコンの形状をブラウザーで確認する。アイコンなしのボタン・リンク・カード・入力欄、および依存をそろえた全件入口でも Angular 版 Lucide の入力寄与がゼロであることを確認する。初期に検索、遅延ルートだけに追加の図形を置き、その図形のコードが遅延側にだけ出ることを検査する。
3. 既定12件、追加登録、別名、同名衝突、親子・同一 injector での登録順、未登録名のエラー、描画後の名前変更を確認する。装飾用アイコンの読み上げ除外、情報を伝えるアイコンのラベル・title、寸法・線・色、内部部品の操作と Lucide 互換入口を実ブラウザーで検証する。
4. 配布候補の `init`・`sync`・`check`、無変更時の再同期、更新時の所有ファイルの追加・削除、同梱データと通知文を確認する。日英ガイドと生成 Skill の少数登録・既定登録・ルート別追加・Lucide 併用の例で `generated-internal-import` が0件、内部ファイルを直接読む対照では警告が出ることを `check --format json` で検証する。元のボードの同一 E2E を新規ブラウザーコンテキストで複数回実行し、既存の5秒条件での通過と取得バイト数を記録する。

登録だけを分割する案、静的な Lucide コンポーネントへの置換、利用側のキャッシュやタイムアウト調整はいずれも、通常の経路から巨大な依存を外せない。上流の Angular 版が型付きの個別入口または軽量描画入口を提供し、同じ配信・互換性の試験に通った時点で、この描画処理を見直す。[上流の個別入口提案](https://github.com/lucide-icons/lucide/issues/5188)
